# x2: game code in Beef, project manager + source SDK

**Status:** plan, 2026-11-06. D1 to D7 approved as recommended; D8 decided by the user (below). Branch x2 is local, kept level with master.

This plan comes from four surveys:
- our code: the scripting footprint; projects, builds and export; the editor, game code and MCP;
- Tallow (main and ecs).

## Target model
- **Game code:** Beef, compiled with the engine. There is no script language and no script interface.
- **What ships:** a standalone project manager, plus the engine as a source SDK.
- **The project's workspace:** each project keeps its layout (Project.xml, Content/, Sources/ for raw assets, Plugins/, export_presets.xml) and adds `Code/`, a Beef workspace with:
  - the game library;
  - per-platform player entry points (the web player builds from it too);
  - an editor entry point;
  - tooling entry points (cook, headless MCP, export).
- **Beef toolchain:** shipped, or required on the system.
- **Export:** builds the player in the project's workspace, then packages it. There are no export templates.
- **MCP:** the editor serves it, with a write-code, build, relaunch and test loop for agents.
- **Hot reload:** investigated separately (phase 8).
- **Raptor:** ports continue for the code we still share. Scripting and export-template commits become N/A.

## What exists already
- **Per-project build:** `ProjectBuild.Generate` writes the project's `Code/` workspace: its BeefSpace, a BeefConfig.toml pointing Beef's registry at the SDK, and under `Code/.generated` the `<Game>Editor`, `<Game>Player`, `<Game>PlayerWeb` and `<Game>Tools` projects, the web player with a workspace of its own in `Code/.generated/Web`. Each has a one-line Main over `Editor.Main`, `Player.DesktopMain`, `Player.WebMain`, or (the tools, by subcommand) `Editor.McpMain`, `Editor.CookMain` and `Editor.ExportMain`.
- **Static plugin parts:** Engine, Pipeline, Tooling and Editor parts register themselves. The host role decides what loads.
- **Native components:**
  - `[SerializableComponent]` with a `SerializableComponentManager`;
  - the inspector, Add Component and the serializer reach them through reflection;
  - the cook, `component_schema` and `scene_validate` use the scene managers.
- **Existing actions:** Add Native Code (`plugin_scaffold`), Build Project, and Open With This Build (it relaunches, then quits this editor).
- **Seams for hot reload:**
  - `SceneModuleContributions` installs into live scenes;
  - `Scene.RemoveSystem`;
  - plugin services record everything a part adds and reverse it on unload.

## Decisions (recommendation first)
- **D1. Tracked or generated workspace.** *Rec:*
  - `Code/BeefSpace.toml` and the game library are tracked and owned by the user;
  - the entry-point projects and the SDK references are regenerated from Project.xml before each build;
  - generated files are git-ignored.

  The alternative is everything generated, as Tallow does.
- **D2. What the game is.** *Rec:* the game is the project's own package. `Code/<Game>` holds the Engine part, with optional `<Game>.Editor`, `.Pipeline` and `.Tooling` parts, and the same self-registration as plugins. `Plugins/` stays for reusable packages.
- **D3. Authoring model.**
  - The scripts used three tiers (Behaviour, Level, Game).
  - *Rec:*
    - a native **Behaviour** tier: a class component with Start/Update/OnDestroy and inspector fields, so the samples' many behaviours port one to one;
    - **Level** as a scene system the game contributes;
    - **Game** as a self-registered run listener (`IRunListener`) in place of `StartupScriptId`.
  - Managers stay the fast path.
- **D4. SDK location.** *Rec:*
  - Project.xml records the engine version;
  - the SDK root is resolved from `SEDULOUS_SDK`, then the manager's registry of installed SDKs, then a checkout found by walking up;
  - paths in generated files are relative where possible.

  It replaces `FindCheckout` and the absolute paths into `Code/`.
- **D5. Toolchain (decided).** No pin for now: we target the Beef nightly (our fixes are all upstream) and keep the build in use unless we hit a bug. A version is pinned when the engine is ready to ship. BeefBuild is found through `BEEFBUILD`, then PATH, then a managed install, checking that corlib is present. Shipping a managed toolchain comes later (phase 7).
- **D6. Win64 export from Linux.** *Rec:* host-native only at first, for Linux and Web, with Win64 built on Windows. Decide on cross-building later.
- **D7. Old script projects.** *Rec:* a data-version bump with MinReadDataVersion. Old files still read, and their script records are dropped with a warning, not refused.
- **D8. The project manager (decided).** It is external to the editor: its own executable, `Sedulous.Tools.ProjectManager`, built from a library split out of Editor.App. It manages several SDKs side by side (installed versions, which project uses which). The editor always opens a project, and Close Project returns to the manager.

## Branch policy (decided)
- master keeps syncing with Raptor (every port, scripting included). x2 is rebased onto master until the new approach is ready.
- Then master is archived as a branch, x2 merges into master, and from there Raptor ports carry only what matters to us. The engines will still overlap a lot.

### Phase 1: the project workspace (`Code/`)
- [x] `ProjectLayout.CodeDir = "Code"`; Add Native Code writes `Code/` (its `.gitignore`, the workspace and the game library).
- [ ] A NEW project is born with `Code/` and its game library, and a root `.gitignore`. **Moved to after phase 5:** while an export still takes a template, a project whose own package is enabled cannot export until built, and never to Web (a template carries no project package), so every new project would lose export. Groundwork: `GamePackage.Scaffold` can take a directory and settings rather than an opened project; the root `.gitignore` is NativeSample's (`/Cooked/`, `/Cooked-*/`, `/.cache/`, `/Dist/`, `/Editor/`, `__pycache__/`); the editor's not-loaded notice for the game's own package should say the project's own editor runs its code.
- [x] SDK resolution (D4) replaces `FindCheckout`. The generated BeefSpace references the SDK's engine projects (through Beef's library registry: a generated `Code/BeefConfig.toml` names the SDK's library folders). `SEDULOUS_SDK`, then the checkout; the manager's registry joins in phase 7.
- [x] Move the remaining Mains into libraries:
  - Tools.Mcp becomes Editor.McpMain;
  - Tools.Cook becomes Editor.CookMain;
  - Tools.Export becomes Editor.ExportMain;
  - Player.Web becomes Player.WebMain.

  The stock tools become one-line Mains over them.
- [x] Generate the entry points (named without a dot: the dotted names are the parts):
  - `<Game>Editor`;
  - `<Game>Player` (desktop);
  - `<Game>PlayerWeb` (wasm32), in a workspace of its own (`Code/.generated/Web`) listing only what a player loads, since BeefBuild compiles every enabled project of a workspace and the editor's dependencies do not compile for wasm32;
  - `<Game>Tools` (MCP, cook and export behind the subcommands `mcp`, `cook` and `export`).

  Each links the game plus the enabled packages' parts for its roles. Build Project still builds only the editor and the desktop player; building the others is phases 2 and 5.
- [x] Migration (NativeSample, the one sample with a package, moved): move an existing `Plugins/<Game>` game package into `Code/` (NativeSample first). `ProjectBuild` keeps reading both during the move.
- [ ] Project templates: Empty (what New Project makes once it writes `Code/`), and Starter (one Behaviour component and a scene, after phase 3). They are reached by New Project and by `project_create`.
- [ ] Tests: generation for every entry kind, SDK resolution, migration, and the .gitignore.

### Phase 3: native game tiers (before removing scripts)
- [ ] The Behaviour component tier (D3): its base class, its manager, lifecycle order, simulation-only gating, and inspector fields via FieldPropertySource. It is prefab and scene serializable.
- [ ] Level tier: a scene-system contribution API for the game. It is listed per scene in the scene's settings, the way SceneScriptSettings was.
- [ ] Game tier: a run listener the game registers. `PlayerApplication` and PIE start it in place of `StartupScriptId`.
- [ ] Native API replacements for what scripts reached only through facades:
  - GUI data binding and commands without script callbacks (Bind/OnCommand on delegates);
  - audio, input, net and http as plain engine APIs.
- [ ] pie_run probes: native equivalents for `script`/`level` (a reflected field of a Behaviour or of the level system). Component probes already work.
- [ ] Tests for each tier, ported from the Engine.Script and GameScript tests.

1. Phases 0, 1, 2, 3 and 4 in order. The workspace and build loop come first, because the samples are rewritten through them.
