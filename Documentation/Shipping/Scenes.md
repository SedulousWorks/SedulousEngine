# Scenes and prefabs

A **scene** is entities in a hierarchy, each carrying components (the transform is
intrinsic; mesh, light, camera, physics body, script, audio source, ... are components). A
**prefab** is a reusable single rooted entity subtree; scenes and prefabs instantiate
prefabs by guid, and the instance re-expands from the prefab source when it loads: edit the
prefab, every instance follows.

## Sources are text

Scene and prefab sources are XML documents stored in the project. That makes them
diffable, mergeable and directly authorable by an agent; the whole MCP scene workflow is
files first: what is in the stored XML IS the scene, no editor needs to be open.

## The exact format comes from the running host

This page explains the concepts only. Anything exact (which components exist, their field
names, kinds, defaults, enum values, ranges, which asset type a reference names, the stream
framing and its version) is generated by the host you are talking to from its own
registrations, so it can never describe a different build:

- `docs://generated/SceneExample.scene.xml`: a complete scene the engine wrote itself, every
  component at its defaults on an entity of its own, every settings block, a parent and
  child, a script behaviour with one override of each property kind. Copy from it.
- `docs://generated/SceneSchema.json`: the schema behind it: the stream framing (`format`),
  every component (`components`, by wire name) and settings block (`settings`, by system id)
  with its fields in wire order, and the script override encoding (`scriptOverrides`). A key
  with no reflected field of its own is listed under `unreflected`; a reference field's `ref`
  says what its guid names (`entity`, or a resource and the asset type to author; when more
  than one asset type makes that resource, a texture's or a render texture's, `assets` lists
  them all and `asset` is the first).
- `component_schema`: one entry of that schema by wire name, type name or system id, for
  when you need one component and not the whole file.

Read the schema once per session; the example is what `scene_write` accepts, because it is
what the engine writes.

## The MCP workflow

- `scene_read` and `prefab_read`: the stored XML by guid. The same text is also exposed as
  read only resources (`project://scene/<guid>`, `project://prefab/<guid>`).
- `scene_validate`: the validation loop when authoring XML. Structure (entities, hierarchy,
  framing) AND component payloads, parsed by the same reader the engine uses with every
  engine manager present. `valid` with empty `warnings` means the engine will load it;
  warnings list genuinely unknown component types (those records would be skipped on load).
- `scene_write` and `prefab_write`: validate first mutation, refused with the full report
  unless the XML passes, stored verbatim on success. Prefabs enforce the single root rule.

## What a scene carries

- **Entities**: id, name, active flag, parent id and local transform, in the order they are
  written (parents before their children).
- **Component records**: the owner entity, the component's wire name, and its data: a data
  version chain first, then the fields. The chain is checked on load, and a stale version
  fails the WHOLE scene load, not one record, so a scene written against an older build must
  be re-saved by the build that wrote it.
- **Settings blocks**, one per scene system that has settings: `physics`, `environment`,
  `postprocess`, `navigation` and `script` (the Level script and its overrides, see
  Scripting.md).
- **Prefab instances**, after the settings: which prefab, where, and the deltas the instance
  applies over its source.

## Script overrides

A script behaviour on an entity binds a script class by guid and can override that class's
declared properties. Each override is keyed by the hash of the property NAME (so a rename in
the class is detectable), then a tagged value: the kind, then the one payload field that kind
uses. The schema's `scriptOverrides` section gives the hash algorithm with a worked example,
the kind table and each kind's payload key; the example scene shows all of them written.

## Scene level behaviour

- The project's startup scene is `defaultScene` in the project settings; `asset_uses` on a
  scene reports that binding under `projectSettingsUses`.

## Gotchas

- A prefab source must have exactly ONE root entity; `prefab_write` refuses multi root
  content with the reason.
- Component records of a type the engine does not know are skipped WITH a warning at load
  and by `scene_validate`: treat any warning as breakage to fix, not noise.
- Deleting an asset a scene references leaves a dangling reference that only surfaces later;
  run `project_health` after destructive changes.
